# 상품 조회 병목: 측정과 수정

## 확인한 원인과 확인하지 못한 부분

기존 정확 속성 검색은 조건 일치 상품을 ID순으로 100개씩 10번 받았다. 이미지/소재 벡터까지 모두 전송한 뒤 Python에서 순위를 계산했다. 반팔 조건에 맞는 상품은 2,889개였지만 첫 1,000개만 비교했다.

`긴팔 말고 흰색 반팔 티셔츠`의 과거 조회 구간 70.24초는 세부 계측이 없어서 당시 시간을 복원할 수 없다. 이번 재측정에서는 70초를 재현하지 못했다. 따라서 당시 원인을 네트워크나 DB 하나로 단정하지 않는다.

동일한 반팔 필터와 고정 설명문 `A plain white short-sleeve T-shirt.`의 임베딩을 사용한 기존 방식 1회 재현 결과:

| 항목 | 측정값 |
|---|---:|
| 조회와 로컬 순위 계산 전체 | 7.051초 |
| 10회 HTTP 응답 헤더까지 대기 합 | 4.007초 |
| 본문 읽기 합 | 2.936초 |
| JSON 해석 합 | 0.040초 |
| Python 벡터 파싱·코사인 계산·정렬 | 0.065초 |
| 응답 본문 바이트 합 | 18,025,776바이트 (약 18MB) |

헤더 대기에는 연결, 게이트웨이, DB 실행과 직렬화 등이 함께 포함된다. 본문 읽기는 애플리케이션 관측 시간이며 패킷 수준 전송 시간과 같지 않다. 위 비교는 기존 SDK 자체를 재실행한 것이 아니라 같은 REST 요청·필터·페이지·벡터 계산을 `urllib`로 재현한 조회 벤치마크다.

별도 `EXPLAIN (ANALYZE, BUFFERS)`에서 마지막 페이지 SQL 실행은 392ms였다. 이 측정은 REST 요청과 다른 실행이며, 벡터의 JSON 변환·전송을 포함하지 않는다. 392ms를 10배하거나 과거 70초에서 빼서 당시 네트워크 시간을 추정하면 안 된다.

## 수정한 흐름

```text
기존: 필터 → ID순 1,000개를 10회 수신(벡터 포함) → Python 점수 계산 → 상위 상품
현재: 필터 → 전체 일치 상품의 DB 점수 계산 → 상위 상품만 1회 수신(벡터 제외)
```

- `filtered_exact_vector_search_768`을 개인 서비스용으로 추가했다. 기존 팀 RPC, 테이블, 인덱스는 변경하지 않았다.
- 소매·기장, 계절·핏 등의 조건과 사용자가 지정한 테이블/세부 카테고리를 먼저 적용한다. 공용은 남성·여성을 모두 포함하고, 다른 배열 조건은 교집합을 사용한다.
- 조건 일치 상품 **전체**의 정확 코사인 점수를 DB에서 계산한다. HNSW 근사 검색이 아니므로 ID 상한이나 근사 검색 후보 누락이 없다. 조건이 없는 기존 HNSW 경로는 유지한다.
- 색상은 설명문 의미 검색에 남긴다. 소재 요청이 있으면 이미지 0.8 + 소재 0.2를 사용하고, 상품 소재 벡터가 없으면 소재 점수는 0이다.
- 요청한 Top-K 상품 정보와 진단값만 반환한다. 기존 후처리와 이미지 URL이 없을 때 Storage 주소를 보완하는 동작은 유지한다.
- 정확 조건에 맞는 상품이 0개면 기존 완화 검색으로 이어지고 그 사실과 시간을 별도로 기록한다. RPC 장애/설치 누락을 조건 완화로 숨기지 않는다.
- 호환용 `/retrieve`도 필요한 컬럼만 조회한다. 기존 방식 벤치마크의 REST·Python 비교 코드는 별도로 남겨 두었다.

조건별 후보를 모두 계산하므로 데이터가 크게 늘면 DB 계산량도 증가한다. 현재 데이터에서 검증한 해결책이며 모든 규모·부하에서 일정한 시간을 보장하는 것은 아니다.

## 수정 후 실제 측정

같은 고정 벡터/필터/Top-3로 새 RPC를 3번 호출했다.

| 항목 | 첫 호출 | 두 번째 | 세 번째 |
|---|---:|---:|---:|
| 조회 호출 전체 | 3.198초 | 0.168초 | 0.220초 |
| DB 내부 전체 | 2.202초 | 0.039초 | 0.039초 |
| DB 필터 | 0.589초 | 0.003초 | 0.003초 |
| DB 점수·정렬·상품 JSON 구성 | 1.585초 | 0.035초 | 0.035초 |
| 응답 크기 | 1,951바이트 | 1,945바이트 | 1,945바이트 |

추가 CLI 검증에서는 1.476초였다. DB·네트워크 상태에 따른 변동이 있어 단일 개선 배율이나 p95를 주장하지 않는다. 기존 방식 1회와 새 방식 반복 측정은 통계적 성능 평가가 아니다.

비교 대상은 첫 1,000개에서 반팔 전체 2,889개로 늘었다. 새 결과의 `5209739`(1위), `4960527`(3위)은 기존 1,000개 범위 밖이었다. 이는 후보 누락 제거의 증거이며 사람 평가로 검색 품질 전체가 향상됐다는 주장은 아니다.

별도로 실제 Gemini 해석·설명 생성부터 로컬 FastAPI `/search`까지 실행한 최종 확인에서는 전체 서버 처리 **4.526초**, 상품 조회 구간 **0.944초**였다. 추출된 조건은 `sleeve=short, color=white, category1=top`, 실제 반팔 결과는 3개였다. 이 실행의 설명문/벡터는 모델이 새로 생성했으므로 위 고정 벡터 비교와 별개다. 배포된 Cloudtype의 사용자 브라우저 시간은 아니다.

## Network 응답 읽기

`POST /search` → Response → `pipeline.retrieval_diagnostics`에 다음 정보가 있다. 정확 필터 경로에서 제공하며, 기존 HNSW 경로의 상세 계측은 이 변경에 포함하지 않는다.

| 키 | 의미 |
|---|---|
| `matched_count` | 벡터가 있고 정확 조건을 만족한 전체 상품 수 |
| `returned_count` | DB가 반환한 상위 상품 수 |
| `db_filter_ms` | DB에서 조건 일치 ID를 모은 시간 |
| `db_rank_ms` | DB에서 벡터 읽기·점수 계산·정렬·상품 JSON 구성을 수행한 시간 |
| `db_total_ms` | 함수 전체 시간. 위 두 값과 함수 처리 비용 포함 |
| `headers_wait_ms` | 백엔드가 HTTP 요청 시작부터 응답 헤더까지 기다린 시간 |
| `body_read_ms` | 응답 본문 읽기 시간 |
| `json_decode_ms` | 수신한 JSON을 Python 객체로 해석한 시간 |
| `http_total_ms` | 헤더 대기 + 본문 읽기. DB 시간도 이 안에 포함 |
| `transport_overhead_estimate_ms` | HTTP 전체 − DB 내부 전체의 차이. 게이트웨이/직렬화/네트워크 등을 포함한 **추정치** |
| `response_bytes` | 수신한 본문 크기. HTTP 헤더나 TLS 오버헤드는 제외 |
| `request_count` | 정확 필터 RPC 요청 횟수 (1회) |
| `fallback` | 일치 상품이 없어 완화 검색한 경우 그 이유·시간. 위 계측과 별도 |

단위는 `*_ms` 모두 밀리초다. DB 시간과 HTTP 시간은 중첩되므로 더하면 안 된다. 전체 검색 단계 시간은 기존 `pipeline.timings`에서 확인한다.

## 재현

저장소 루트에서 기존 백엔드 환경변수를 읽어 실행한다. 기본 실행은 임베딩 1회와 새 RPC 3회이며 읽기 요청만 한다.

```bash
.venv/bin/python -m pipeline.benchmarks.retrieval_diagnostics
```

기존 대용량 조회까지 비교하려면 `--legacy`를 추가한다(약 18MB 전송). 고정 벡터 JSON 배열을 `--embedding-file 경로`로 지정하면 임베딩 API 호출을 생략한다. 결과는 기본 `.omx/state/retrieval/diagnostics.json`에 저장하며 키/상품 벡터는 기록하지 않는다.

검증: 백엔드 105개, 프론트 21개 테스트와 lint/build/컴파일 통과. 실제 DB에서 바지·원피스·전체 카테고리, 공용·여름 조합, 0건, 소재 가중 점수를 확인했다. 소재 가중 결과의 ID/점수는 별도 직접 SQL 계산과 같았다. 새 함수의 실행 권한은 `service_role`만 갖고, 기존 팀 함수 정의 해시는 변경 전후 같았다.

DB 함수는 적용했다. 백엔드 코드는 커밋·푸시·Cloudtype 배포 전이므로 배포 사이트에 적용하려면 코드 배포가 필요하다.
